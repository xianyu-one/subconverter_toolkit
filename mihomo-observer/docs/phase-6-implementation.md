# Phase 6：后端 MVP 实现

状态：本文记录 Phase 6 后端实现时的状态。后续 Docker、Web UI 与分票验收进展见[曳光弹票据](tracer-bullets.md)末尾；真实 FlClash 集成仍需用户设备验证。

## 实现与原因

单进程 Go 服务以配置文件启动。Collector 定时读取 `/connections` 完整活动快照，整帧解码后放入容量为 1 的最新帧邮箱，SQLite Writer 用单个事务更新原始连接、每连接小时贡献、缺口及 checkpoint。队列溢出、请求/解码失败或写入失败会打断连续性；恢复时以现有累计值建立新基线，旧活动连接未再次出现时标为未知。首次累计值也仅作基线。`/version` 低频查询并记录实际核心版本。

Phase 4 原设计优先 WebSocket。当前选择相同完整快照语义的 `GET /connections` 每秒轮询，减少首版依赖和协议实现量。代价是每秒一次 HTTP 请求，需在真实 FlClash 上观察 CPU/请求开销；未来可在不改状态机与数据库契约的前提下替换传输。全局流量首版使用连接快照附带的总计，不连接独立 `/traffic` 流；重置与缺口不补算字节。

SQLite 采用 WAL、`synchronous=NORMAL`、外键与 busy timeout。Schema 从 Phase 2 设计 DDL 转为 `0001` 迁移。每个采集帧是事务边界，分析与投影另行运行。小时/日报表由 `connection_hours` 生成，日界线使用固定报告时区。Raw 清理每轮最多 5000 条；历史聚合不依赖已清理 raw。窄 `Store` 接口隔离业务与 SQLite；当前只有 SQLite 实现。

Analyzer 只读取已完成小时。重复连接需相隔至少五分钟的两次分钟级密集峰值；小流量长连接还需重复证据。IPv6/IPv4 比较要求同域名来源、路径、网络和目标端口，两侧各至少 20 条、至少两个小时，并达到差异门槛。Problems 包含计数、严重程度、把握度与建议检查方向，避免推断实际失败、协议回退或错误分流。问题重算会撤回最近七日不再成立的 occurrence，保留较早历史。

API 从第一版就要求 Basic Auth，默认只监听本机。用户允许监听所有接口，配置中可指定 `0.0.0.0`；远程访问时凭据应经过 TLS。所有查询只读。Web UI 的详情图表将在 Phase 8 使用这些 API。

## 取舍与未完成项

- 尚无真实 FlClash 脱敏快照，因此 `chains` 顺序和部分可选 metadata 只按 Mihomo 官方字段解释；不从名称猜测最终代理节点。
- Analyzer 对单轮最近七日原始输入设置 100000 条上限与 20 秒超时；超限时保留旧结果并报告错误。大流量场景需要以预聚合候选替代全量扫描。
- 目前只有路径级统计，没有 `/proxies` 目录、独立 `/traffic` 流、主动验证或自动规则生成；这些属于后续可选扩展，不影响被动证据记录。
- Basic Auth 密码在本地配置文件中，部署时应限制文件权限。远程裸 HTTP 会暴露凭据，Phase 7 Docker 文档需要明确网络边界。
- 单 SQLite 连接串行化写入和分析，保持实现简单；真实负载若出现明显采集延迟，再拆分 WAL 读写连接或优化分析任务。

## 验证

`go test ./...` 覆盖字段解码、首次累计值与连续增量、空快照消失、缺口不误判、小时投影、两次密集峰值、IPv6/IPv4 充分样本对比及未授权 API 拒绝。尚未进行真实 FlClash、Windows、长期运行或高连接数负载测试。
