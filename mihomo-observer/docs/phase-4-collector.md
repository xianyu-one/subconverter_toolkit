# Phase 4：Collector 设计

状态：设计完成，尚未实现。以 [Phase 3 API 模型](phase-3-mihomo-api-model.md)为输入，以 [Phase 2 Schema](phase-2-schema.md)为持久化契约。首版针对一台 FlClash 承载的 Mihomo；实际版本和脱敏响应仍需在实现前核验。

## 目标与边界

Collector 持续读取完整活动连接快照，留下可解释的已观测历史，同时把断线、丢样和数据库故障显式记录为缺口。它不解释连接为何慢、不判定错误分流，也不触发主动延迟测试。采集任务分为连接、全局流量和低频代理目录/版本信息；连接与流量失败互不阻塞。

## 进程内流程

```mermaid
flowchart LR
    A[/connections WS] --> D[解码与整帧校验]
    D --> Q[有界最新帧邮箱]
    Q --> R[快照协调器]
    R --> W[单 SQLite 写入器]
    T[/traffic] --> G[流量基线与缺口]
    G --> W
    V[/version 与 /proxies] --> C[版本与代理目录]
    C --> W
    W -->|提交成功后确认| R
    W --> DB[(SQLite WAL)]
```

连接读循环只做网络读取、大小限制、解码和整帧校验，不等待 SQLite。它把最新的**完整帧**放入容量有限的邮箱；邮箱满时替换尚未处理的旧帧，累计丢样数和时间范围。协调器只以成功提交的帧为已处理状态；写入失败时不推进活动连接集合或累计字节基线。这样既不会无限占用内存，也不会因丢帧把旧连接误判为正常结束。

写入器以一帧作为一个逻辑批次，用**一个事务**更新该帧涉及的连接原始记录、每连接小时贡献、dirty bucket、checkpoint 和缺口。事务内部可分块执行 SQL，但不得分批提交一帧；只有整帧提交成功才回 ACK。桌面单实例的预期规模允许这种事务边界；如实际帧过大，先记录采集能力不足，而不是悄悄拆成无法保证完整性的半帧结果。分析器的问题更新走低优先级写入请求，不能排挤连接采集。

快照不附带服务端采样时刻。每帧解码成功后记录本机 UTC 接收时间与单调序号；写入器在事务中持久化 `last_frame_seq`。序号用于防重，墙上时钟只用于展示和时间桶。若系统时钟回拨或前进异常，标记时间异常缺口，不计算跨异常时段的活动时长。

## 连接状态转换

| 前一状态 | 本次完整帧 | 处理 |
| --- | --- | --- |
| 未见过 | 出现 | 新建已观测连接；保存首次累计字节为基线，目标级增量为 0；记录首次观测时间 |
| 连续有效帧中可见 | 再次出现 | 身份、计数器和稳定端点有效时更新最新值；非负字节差额记入本帧小时；连续观测时间计入活动时长 |
| 连续有效帧中可见 | 消失 | 记 `absent` 与发现其消失的时间；不设置精确 `ended_at` 或失败原因 |
| 上一帧之后有断线、丢帧或写入失败 | 出现 | 恢复同一身份时保留历史，但本次计数只重设基线；不计跨缺口时长或字节增量 |
| 上一帧之后有缺口 | 未出现 | 旧连接标 `unknown`；不能用不连续快照断定何时消失 |
| 同 ID 的已知 API 开始时间、稳定目标端点或计数器明显冲突 | 出现 | 结束旧观测身份并开启新身份；开始时间未知时依赖观测世代并更保守地处理跨断线连续性；不写负字节差额，也不覆盖旧记录 |

只有完整有效的帧可以推动“消失”判定。官方 Mihomo 可能在无活动连接时发送 `"connections": null`；它是有效空帧，而缺失字段、错误类型、重复 ID 或局部解码失败的帧不是。`host`、`sniffHost`、目标 IP 或 ASN 晚到时，协调器向写入器提交有限期重归组操作；规则或代理链变化时保留实际路径，不能用最新路径覆盖旧小时的贡献。目标 IP 初次缺失后补齐可重归组，已确认的 IP 变为另一个 IP 则视为身份冲突。

第一次订阅快照可能包含很早就开始的连接。原始行保留 API 当前累计值和首次基线，统计贡献从下一次连续有效观测开始。采集缺口后的首帧也仅重设基线；这会低估目标级流量，但不会把 Observer 未看见的流量错误归到恢复小时。Dashboard 的全局流量同样只计算 `/traffic` 连续样本之间的非负增量，并把缺口公开显示。

## Controller 连接与重试

- 使用配置的 Controller 基础 URL 构造 `http(s)` 与 `ws(s)` 地址；WebSocket 握手使用 Bearer Header，不把 secret 放在查询参数、日志或浏览器。连接超时、读取超时、帧大小上限和关闭握手均受 `context.Context` 管理。
- `/connections` 首选 WebSocket，设置合理的 `interval`（默认沿用 Mihomo 的约 1 秒），并验证首帧到达。WebSocket 不可用时可用 `GET /connections` 定时轮询，但仍按完整快照处理；身份验证失败与接口不存在要在状态页给出不同原因。
- 网络错误采用有上限的指数退避与随机抖动；成功稳定运行后重置退避。重连后的首帧建立新连续区间，不能跨断线补算活动时间或请求结果。
- `/traffic` 独立连接，首样本设全局总计基线。`upTotal`/`downTotal` 回退意味着计数器重置或核心重启，开启新基线；即使累计值增长，也不把断线期间的增量归入恢复时刻。
- `/version` 在建立连接时低频读取，保存实际核心版本与是否 Meta；`/proxies` 低频刷新当前代理目录。两者失败不停止连接采集；当前目录也不反写历史代理路径。
- FlClash 当前生成的 Controller 默认为关闭，开启后绑定 `127.0.0.1:9090`。Windows 原生 Observer 与其同机连接；Docker 只部署在容器可达 Controller 的环境。Observer 不尝试修改 FlClash 运行配置。

## 队列、写入与恢复

连接邮箱保留至多一个正在处理帧和一个待处理最新帧；流量邮箱也有固定上限。参数可调，但默认绝不无限缓存。任何替换、解码失败、帧过大或写入失败都增加相应计数，并形成带起止时间的 `collection_gaps`。若队列满时无法立即写入数据库，进程内保留待报告缺口；下次成功提交时持久化。进程在此之前崩溃，启动时根据 `collector_checkpoint.last_committed_at_ms` 补记不确定缺口。

写入器是 SQLite 的唯一高频写入口。一个连接帧的 SQL 更新和 checkpoint 必须原子提交；提交前不确认帧，也不推进协调器的已提交连接集合。重启时加载 checkpoint 与仍处于活动/未知状态的连接，增加单调帧序号；启动首帧建立新连续区间。每条连接的累计计数以上次持久化值为准，避免重连重复记字节。分析器和聚合器的写入采用可重试低优先级任务；采集停止时排空已接收任务并在超时后留下可见缺口。

为保护桌面客户端，限制单帧字节数、连接条数与代理目录响应大小；超限时拒绝整帧并记录原因，不因恶意或异常响应无限分配内存。日志只保留错误类别、计数和时间，不打印原始 JSON、secret、进程路径或完整 URL。

## 可见状态与验证用例

状态 API 至少报告连接流和流量流各自的状态、最后有效帧与最后成功提交时间、实际 Mihomo 版本、当前已观测连接数、采集间隔、队列丢帧数、解码错误数、写入错误数和最近缺口。断线时“当前连接数”显示未知或过期时间，不显示为 0。

Phase 6 实现时，使用可控的 Controller 假流覆盖下列行为：

1. 首帧已有累计字节；第二帧增长；第三帧 `connections: null`，确认只计算第二帧差额且第三帧只标记消失。
2. 连接仅有 IP，后续出现 `sniffHost` 或 `host`；归组来源可追溯，保留期内贡献被修正。
3. WebSocket 中断、邮箱替换帧、SQLite 提交失败后恢复；不跨缺口补算时长和字节，也不误标 `absent`。
4. 同 ID 不同开始时间、目标 IP 明确变化、计数器回退、重复 ID、局部坏数据和整帧坏数据；旧记录不被覆盖。
5. 跨小时、跨日和系统时钟回拨；增量进入正确桶，异常时间形成缺口，日连接数不重复累加。
6. `/traffic` 总计重置、`/version` 与 `/proxies` 失败、Collector 停止和重启；连接主流程仍可运行或明确显示缺口。

## 取舍与未来扩展

整帧事务使“谁出现、谁消失”与字节增量保持一致，代价是单帧写入时间受活动连接数量影响。最新帧邮箱保护内存和 Mihomo，但在拥塞时牺牲时间覆盖率；缺口指标让这种牺牲可见。首次累计值仅作基线使统计偏保守，避免时间归属造假。将来若真实客户端的活动连接规模超出单帧事务能力，应先测量写入与采样开销，再考虑耐久化帧日志或分片方案，不提前引入分布式组件。
