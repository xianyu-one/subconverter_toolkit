# Phase 2：SQLite Schema 设计

状态：可审阅的设计。完整 DDL 见 [phase-2-schema.sql](phase-2-schema.sql)；Phase 3 将用实际 Mihomo 客户端响应验证可选字段，再把 DDL 转成正式迁移。

## 数据口径

- 所有时间用 UTC Unix 毫秒整数；小时桶按 UTC 划分。日桶以首次启动时固定的 `reporting_timezone` 的当地零点划分，桶键仍存该零点对应的 UTC 毫秒。报表时区是必填配置，例如 `Asia/Taipei`；首次启动后写入 `observer_settings`，以后更改需要重建历史日统计，不能静默混用。`last_seen_at_ms` 是最后观测时间，`disappearance_seen_at_ms` 只是下一次连续快照中未再出现的时间，均不是精确连接结束时间。
- 原始字节数是最近一次快照中的累计计数，另记首次看到时的计数基线。目标级汇总只累计两个连续有效观测之间的非负字节增量，首次看到时的已有字节不归入当前小时；全局流量从 `/traffic` 单独采集。未知值用 `NULL` 或明确的 `unknown`，不写入伪造的失败、延迟、DNS 域名或最终代理字段。
- 域名优先取 `host`，其次 `sniffHost`；两者都没有时归为 IP-only。原始表分别保留 `host`、`sniff_host`、`target_source`，避免丢失来源。ASN 可空，IP 版本 `0` 表示未知。
- 保存白名单字段，不保存完整 metadata JSON。源地址、进程名称与路径只有启用相应隐私选项时才写入；凭据、URL 参数、HTTP 内容不写入任何表。

## 表与查询职责

| 表 | 保存什么 | 主要用途 |
| --- | --- | --- |
| `observer_settings` | 固定的报表时区 | 保证“今日”及长期日统计使用同一日界线 |
| `observation_epochs` | 观测身份不连续的世代及可选的 Controller 版本 | 防止 Mihomo 重启或连接 ID 复用覆盖旧记录；普通 WebSocket 重连可延续既有连接，版本便于排查字段差异 |
| `collector_checkpoint`、`collection_gaps` | 最后成功提交位置、流量计数基线和缺口 | 重启恢复、显示采集完整性；断线后不把未知时段补成零 |
| `route_paths` | 规则、规则载荷、代理链的规范化组合 | 多连接共享路径；`0` 为汇总所有路径，`1` 为路径未知 |
| `connections_raw` | 每条已观测连接的最新状态和白名单元数据 | 最近 14 天的详情与分钟级重复连接分析 |
| `connection_hours` | 每条连接每小时、每条观测路径的字节和观测时长贡献 | 支持跨小时统计、连接去重和域名晚到后的有限期重归组 |
| `projection_dirty` | 需要重算的小时或日期及版本号 | 聚合失败后重试；避免并发采集时用旧结果覆盖新数据 |
| `analyzer_checkpoint` | 最后完成的分析窗口 | 分析器重启后补算；近期窗口定期重算以吸收晚到元数据 |
| `stats_hourly`、`stats_daily` | 目标、目标 IP、ASN、代理路径的已观测汇总 | 长期趋势和 Web UI 查询；日连接数从贡献记录直接去重计算 |
| `global_traffic_hourly`、`global_traffic_daily` | `/traffic` 的全局已观测增量 | Dashboard 今日总流量；与目标级流量分开 |
| `problem_records`、`problem_occurrences` | 问题身份、目标/路径/端口/协议范围、严重程度、证据把握度与按窗口保留的历史证据 | Problems 及历史回顾；近期状态由最后实际证据时间计算，不由分析任务运行时间计算 |

`stats_*` 的 `subject_kind` 分为 `domain`、`ip_only`、`destination_ip`、`asn`、`proxy_path`。一个连接可同时进入“目标 IP”和“域名”视图，因此**不同 subject_kind 的流量绝不能相加**。对域名或 IP-only 的路径拆分，`route_id = 0` 表示不区分路径的唯一连接总数；路径行用于解释差异，也不能跨路径简单相加。`proxy_path` 表示完整观测路径，首版不推断单个节点的独立性能。

`observed_active_ms` 只累积连续采样之间可观察的活动时间，不是精确连接时长。统计表不保存失败率或长期时长中位数：Controller 没有失败事件，而单纯保存时长和连接数无法还原中位数。最近 14 天如需参考中位数，只能从原始记录计算“观测跨度”的中位数，并明确其采样偏差；长期分位数需要后续增加直方图或可合并的摘要结构。

## 写入和聚合事务

一个采集批次在同一事务中执行以下操作：

1. 用观测世代、Mihomo 连接 ID 与可用的 API 开始时间组成稳定 `identity_key`；开始时间缺失时只在当前连续观测区间内信任 ID。WebSocket 重连后若身份仍一致，继续更新同一行；计数器回退、明确变更的目标 IP/协议或身份不明时开启新身份，不将负差额写入统计。初次缺失而后补齐的 IP、ASN 不算目标变更，可在保留期内重归组。
2. 与已持久化的累计字节比较，计算非负增量。首次看到的累计值只记作基线；跨采集缺口恢复后的第一个值重新设基线，不把缺口内流量塞进恢复时的桶。持久化的 `last_frame_seq` 是幂等边界，`last_sample_at_ms` 仅作观测时间，不依赖可回拨的墙上时钟防重。
3. 更新 `connections_raw`，并更新对应 `connection_hours`。字节增量归入当前观测时刻的小时；连续观测到的活动时长在跨小时处切分，采集缺口不计为活动时长。
4. 若后续快照才得到 `host`、`sniffHost`、目标 IP 或 ASN，更新保留期内该连接的贡献记录的对应归组；代理路径在每次观测时记录，路径变化可在同一小时形成多条贡献。受影响的小时与日期进入 `projection_dirty`。
5. 更新采集 checkpoint、流量桶和缺口；连同原始记录与贡献记录一次提交。事务失败则整个批次不生效，恢复时可从持久化计数基线继续。

从连续活动快照中消失的连接可标为 `absent`，并记录发现其消失的时刻；经过采集缺口而不再出现时标为 `unknown`。两者均不表示连接失败。活动连接不会因为保留期到达而被删除。

聚合器读取 dirty bucket 的 `revision`，从 `connection_hours` 重算该桶的所有 subject 行，在一个事务内替换旧行并清除 dirty 标记。若提交时 revision 已变化，则保留 dirty 标记并重试。小时和日统计都直接从贡献记录计算：**不能把小时连接数相加当成日连接数**，因为长连接会跨小时出现。当前小时或日期可节流刷新，UI 显示最后更新时间。

晚到的域名只在贡献记录仍存在时重归组；默认可修正最近 14 天。更早的已保留聚合不承诺被新元数据重写。这是短期原始数据和长期统计之间明确的修正边界。

## 索引、保留与迁移

`connections_raw` 按首次/最后观测时间、目标、路径建立索引，服务最近数据查询和分批清理；`connection_hours` 按桶建立索引，服务聚合重算；统计表以 `(桶, subject, 路径, IP 版本, 协议)` 为主键，并以 subject/路径加时间的索引服务详情；问题表按最近出现时间和目标索引。索引数量保持有限，避免每次采集更新承担过多写放大。具体查询计划在 Phase 6 用实际数据量检查。

默认保留：`connections_raw` 与其 `connection_hours` 为 14 天，`stats_hourly` 为 180 天，`stats_daily` 和问题历史永久。所有天数可配置，`0` 表示永久。清理顺序为：先完成待清理桶的聚合，确认没有未处理的 dirty bucket，再小批量删除已不活动的原始行及其贡献记录，最后清理过期小时统计。问题历史只保存经白名单验证的指标摘要，不复制原始连接内容。

程序打开数据库时设置 `journal_mode=WAL`、`synchronous=NORMAL`、`foreign_keys=ON` 和合理的 `busy_timeout`；这些是连接设置，不写进迁移事务。正式实现采用按版本顺序执行的事务迁移，并拒绝打开版本高于程序支持范围的数据库。迁移前备份使用 SQLite 在线备份能力或安全的停机复制方式，不直接复制正在写入中的单个 `.db` 文件。

## 为什么这样设计

每条连接只保留一行原始记录，避免每秒完整快照迅速膨胀；`connection_hours` 作为短期派生账本，解决跨小时流量与晚到域名的归组问题。代价是多一张随原始记录清理的表和一个可重试的聚合步骤。相比永久保存全部快照，它的长期资源占用更可控。

`stats_*` 使用同一组列表示几种明确的 subject，而不是为每种维度复制一套表。这样保持首版 schema 较小，同时 subject 的枚举和查询接口仍是固定的；将来若确需 CDN Provider 或 IP Prefix，可新增 subject 类型及迁移，不提前建设外部归属数据库。PostgreSQL 仍不在首版范围内。

Phase 3 需要重点验证 `started_at`、`sniffHost`、ASN、代理链、流量总计在实际客户端上的可用性；不符时调整可选列映射和迁移设计，不补造 API 没有的数据。
